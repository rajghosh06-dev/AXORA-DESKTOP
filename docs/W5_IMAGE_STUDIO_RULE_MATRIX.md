## 1. Authority and evidence vocabulary

This matrix turns the Product Contract and Technical Architecture into 36 testable rules. A rule cannot pass because a test executes literal `Assert(true)`, a forced-pass branch succeeds, a probe merely completes, a non-executing rule statement exists, or one configured machine happens to provide an optional codec. Environment-unavailable and policy-skipped are justified non-pass dispositions; a bounded runtime observation proves only the observed path.

Only these evidence labels are used:

- `AUTOMATED DETERMINISTIC` — stable headless logic with an externally observable oracle;
- `AUTOMATED INTEGRATION` — service, filesystem, codec, or application-boundary behavior;
- `STATIC AUDIT` — named source, dependency, traceability, or diff inspection with a retained checklist;
- `RUNTIME OBSERVATION` — measured runtime behavior that is not promoted to a universal guarantee;
- `UI AUTOMATION` — an executing WinUI surface, not a ViewModel substitute;
- `MANUAL VISUAL/ACCESSIBILITY` — retained visual/accessibility checklist and screenshots where useful;
- `ENVIRONMENT-DEPENDENT` — capability evidence tied to recorded host prerequisites.

`Core` means required W5 behavior. `Conditional` means the rule governs a capability only if its proof gate accepts that capability. `Deferred` means the rule verifies that the capability is not exposed as W5 core.

## 4. Acceptance interpretation

- Conditional codec success on one machine does not satisfy universal core support.
- An environment-unavailable result is a reasoned skip/conditional classification, not a pass for functionality.
- Static and manual rules require a named retained artifact; they do not inflate automated assertion counts.
- Performance observations never override deterministic safety failures.
- All 36 rules must end with meaningful evidence or an explicit blocked/deferred disposition before W5-F acceptance.
